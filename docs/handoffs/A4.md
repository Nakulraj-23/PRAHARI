# A4 handoff: serving API

## What exists
- `prahari/serving/`: `app.py` (`create_app`, `app`; all CONTRACTS endpoints + `GET /v1/kpi`), `incidents.py` (detector + approve/reject), `services.py` (model registry, validate/anomaly/RCA wrappers), `data.py` (label-free SQL), `obs.py` (request-id, JSON logs, per-endpoint latency histogram in `/metrics`, typed errors `{"error":{type,message,request_id}}`).
- Models load once in lifespan via `load(settings=...)` and are used only through `predict(payload)`. A missing model gives 503 on its endpoints only. CORS for :5173/:3000 (`Settings.cors_origins`).
- Detector (every `detector_interval_s`=10 s): new alarms (cursor = last alarm_id, kept in `audit_log`) -> validator -> valid alarms clustered (<=5 min, <=2 hops, >=2 alarms) -> RCA (15 min window starting 5 min before the first valid alarm) -> agent -> full 10-check governance -> row in `detected_incidents` + `actions` (+ `predictions`, `audit_log`). A cluster near an open incident joins it and re-runs RCA while its action is undecided.
- Decisions: approve -> `sim.apply_action`, status `executed`, incident `resolved` if the sim recovered. `blocked` approve = 409; already-decided = 409; reject is logged with the note. `auto_approved` governance decisions execute immediately (audited).
- Shared-file edits (orchestrator-requested): `db.py` (+`actions.created_at`, +`detected_incidents`, `ensure_schema` adds the column to old DBs, sqlite timeout 30 s), `config.py` (`llm_provider` default `none`, cors/detector settings), `schemas.py` (+KpiResponse, LatencyStats, ModelInfo, ErrorResponse), fixtures (`kpi.json`, `models.json` with latency, 10-check governance in `incident*.json`/`action_decision.json`, G2 = `top1_top2_margin`, G4 = `action_allowlist_blast_radius`), `Makefile serve`.
- G9 `recent_actions` = other incidents' proposed/approved/executed actions from the last 60 min (from `actions.created_at`).
- `/v1/models`: card metrics flattened to floats (`test.root_top1`) plus `latency` {count, mean, p50, p95, max} from the last 500 `predictions` rows per model (model-reported ms, not HTTP time).
## Run
`make serve` (needs `make seed` and trained models). Tests: `.venv/bin/pytest tests/serving` (~26 s; builds a 1-day DB, links real artifacts). Serving path never reads `label_*` or `incidents`: checked by a SQL-capture test and a source scan.
## Measured (1-day DB, 120 nodes, CPU)
- 10 injected faults, real detector loop at 1 s: 8 detected; root top-1 8/8, fault type 8/8; 7 of 8 approved and recovered, 1 blocked (409 on approve). 2 not detected (leaf CELL/ACC faults with < 2 valid alarms in 25 s). Detection latency median 1.0 s after inject (max 25.4 s).
- Median endpoint latency: `/v1/alarms` (50) 6.7 ms scored-cached, `/v1/rca` 63 ms, `/v1/models` 4.8 ms. Model latency: validator p50 27.7 ms / p95 50 ms (10 calls); RCA p50 118 ms / p95 288 ms (14 calls). Small samples.
## Concurrency fixes (after A6 load test)
- `get_engine` sets SQLite WAL, busy_timeout 30 s, synchronous NORMAL. Prediction-log writes never fail a request; `database is locked` anywhere returns 503 `database_busy` + `Retry-After: 1`, never 500. Detector/handlers use short sessions.
- `/v1/rca` caches per (window, counts, model version) for 30 s, one compute per window, at most 2 concurrent feature builds. `make train` now runs `drift build-reference`.
- Load test, 90-day DB scratch copy, 12 s/level, A6's script, 0 errors everywhere: /v1/rca 1 client p50 95.7 / p95 243 ms; 8 clients p50 3.7 / p95 1581; 32 clients p50 8.6 / p95 2354 (116 req/s, mostly cache hits: the pool reuses windows, so uncached cost is ~100-250 ms). /v1/alarms/validate p50/p95: 54.9/74.5 (1), 1060/1987 (8), 4513/6986 (32); not cached, CPU-bound on 4 shared cores, throughput 17.6 -> 6.5 req/s.
- Q3 fixes: approve re-runs all 10 checks (`governance.evaluate`) and returns 409 on any fail, marks the action blocked, audits `approval_blocked_by_governance`. New cluster joins an open incident (<=60 min) if its RCA top-1 is that incident's root or downstream. `/v1/rca` window <= 6 h and 422 `no_data` without KPI; validate <= 1000 alarms, no duplicate ids, alarm_type enum; decision `user` min_length 1; `run_drift(settings=...)`; agent SQL 2 s progress-handler timeout.
- Docker: CPU torch in Dockerfile, web/Dockerfile (nginx), compose api on SQLite volume, one-off `docker compose --profile setup run --rm setup`, Postgres optional/untested. Not built (disk).
- Regression tests (22 in tests/serving): WAL pragmas, 96 requests on 32 threads give no 5xx and RCA computed once per window, lock error gives 503.
## Known gaps
- Misses above = MIN_ALARMS=2; single-valid-alarm faults wait 15 min then drop.
- Validator KPI z-scores are recomputed in `serving/data.py` (copy of the pipeline definition); drift if A1/A2 change it. Anomaly gets 240 min of history (retries once if a model asks for more).
- `/v1/drift/run` calls `run_drift(settings=...)` and reads the latest `drift_reports` row; 503 until it exists. Docker Compose/Postgres path not run here.
- `no_action` approvals execute nothing. Not tested against the 90-day DB or with a real LLM provider.
