# A1 handoff — simulator and feature pipeline

## What exists
- `prahari/sim/`: `topology.py` (networkx generator, `NetworkModel` array view; MAIN 120 nodes seed 42, ALT 80 nodes seed 7), `kpi.py`, `faults.py` (propagation, KPI effects, scheduling, symptomatic alarms), `alarms.py` (noise, vendor raw_text: Nexa/Orion/Zenith), `generate.py` (CLI), `live.py` (`LiveSimulator`: `inject`, `apply_action`, `scenario("firmware_drift")`, `tick`, `reset_scenarios`), `constants.py`.
- `prahari/pipeline/`: `store.py` (`load_kpi` -> (T,N,6) tensor, `load_alarms` label-free allow-list, `load_ground_truth_incidents` training-only), `features.py` (`build_alarm_features(df, net, kpi)`, `build_node_window_features(start, end, settings)`, `build_incident_graphs(settings, split, window_minutes=15, with_ids)`, `feature_names()`), `quality.py` (`run_quality_checks(engine)`, raises `DataQualityError`), `splits.py` (`make_splits`, `load_splits`).
- Tests: `tests/test_sim.py`, `tests/test_pipeline.py`. 32 pass in ~14 s (with A0's), ruff clean.

## How to run
`make seed` (90-day main DB `prahari.db` + 7-day alt DB `prahari_alt.db`, splits to `artifacts/splits.json`; default 6.5 incidents/day). Alt only: `python -m prahari.sim.generate --alt --days 7`. Node order everywhere = sorted node_id. Seed resets the whole DB (drop_all).

## Measured (seed 42, 30 days, after Q1 fixes F1-F7)
- `make seed` (90 days + 7-day alt): 254 s total (main 240 s incl. 60 checks; alt 11 s). Over the original 3 min target; `--days 30` takes ~80 s. Checks pass on both DBs.
- 584 incidents (90 days, 6.5/day): congestion 154, fibre_cut 111, config_error 110, hardware_degradation 110, power_failure 99. Split 408/88/88 chronological.
- 6393 alarms, 15,241,049 KPI rows (DB 2.3 GB) (2% of samples missing, AR(1) phi=0.7 noise). Noise ratio 25.0%; true alarms/incident mean 8.2, median 6.
- Root alarm missing 13.5%; ~10% of incidents start during an earlier one (19.5% intersect another).
- Q1 probes (30-day plan, time split 70/30): kpi_z_max depth-2 tree AUC 0.846 (was 0.976); HistGB on all alarm features still 0.995 (flapping/neighbour counts separate noise: expect easy validation). Largest-d_latency node = root 52.8% (was 82.9%); d_packet_loss 61.8%; jittered windows 51.7% / 61.2%; alarm_total argmax 51.7%.
- All 15 alarm types and 3 severities occur in both classes. 30% of noise alarms get a 3-8 min KPI blip; 40% of dependents (10% of roots) show ~no KPI change; per-incident magnitude/gain via `fault_gain`.
- Timings: full KPI load 19 s; `iter_incident_graphs`/`build_incident_graphs` 584 incidents in 81 s, peak RSS 1.4 GB (chunked 8 days at a time; output identical to A3's `build_graphs_chunked`); one window query 0.07 s on the 90-day DB (was 1.4 s: SQLite scanned the whole kpi index; `load_kpi` now pins the join order, no new index needed).
- Tests: 73 pass (~60 s), ruff clean, no xfail left.

## Known gaps
- Synthetic data: model accuracy here is not real-network accuracy. True alarms still all arrive within ~6 min of fault start. Q1 probe numbers below were measured on the 30-day plan (same seed and settings, first 30 days of the 90).
- `build_incident_graphs` jitters window starts U(0,10) min earlier (`window_jitter_min`, seeded; 0 disables). Live `inject`: root alarm dropped 15% of the time, tier random per fault, faults rebuilt after restart from incident_id (deterministic gains).
- Live writes are not one transaction. Window query has no ts index (see EXPERIMENTS.md). `ruff format` also touched whitespace in A0's config/db/schemas.
